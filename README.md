# The Uneven Cost of Compression

Quantization and batching trade-offs in an embedding inference service.

CS 5130 (Programming and Data Processing for AI), Fall 2026 · Theme 5: Model Optimization & Efficient Inference Systems
Devansh Jignesh Nayak · Venkatashivasai Muppidi

## Purpose

An embedding inference service (text in, vectors out) built around
`BAAI/bge-small-en-v1.5`. Numeric precision (FP32, FP16, INT8, 4-bit NF4) and
batch size (1, 8, 32, 128) are configuration of the running service. The
project measures latency, throughput and memory across those settings, and
asks whether compression's quality loss is spread evenly or concentrated on
rare and easily confused inputs (Banking77, SciFact).

## Code organisation

```
src/uneven_compression/
    ingestion.py    load a labeled task, validate it, produce a request queue
    batching.py     group requests into batches of a configured size
    serving.py      load the model at a configured precision, embed batches
    storage.py      persist embeddings and timing logs by configuration
    evaluation.py   quality and efficiency metrics
    timing.py       GPU-synchronised latency, throughput and peak-memory harness
    analysis.py     where the quality cost lands: rare vs common intents, FP32 margin
scripts/            the experiment, one script per step (see "Reproducing the results")
slurm/              job files for Explorer's V100 nodes
figures/            report figures (generated by scripts/make_figures.py)
tests/              unit tests (pytest)
```

## Classifying new messages (the service on unseen data)

Give it a CSV with a `text` column (an `id` column is optional):

```bash
pip install -e ".[model,analysis]"
python -m uneven_compression classify examples/new_messages.csv --out predictions.csv
```

```
id         intent                              conf margin  risk  text
m01        card_swallowed                      0.36  0.248        The ATM ate my card this morning and didn't g...
m14        top_up_by_bank_transfer_charge      0.16  0.067  YES   Is there a limit on how much I can transfer i...
m18        failed_transfer                     0.19  0.046  YES   My bank transfer to my landlord was rejected ...

2 of 18 messages at risk (margin < 0.1) on mps
```

Each message gets its Banking77 intent, the classifier's confidence, the
runner-up intent, and its **margin** (confidence minus the runner-up's
probability). Messages with a margin below `--risk-margin` (default 0.10) are
flagged: in our quality study, every prediction NF4 changed had an FP32 margin
below 0.083, and none of the 2,749 test messages with margin 0.10 or more
changed. The flag tells you, before deploying a compressed model, which
messages it may answer differently. It is not a correctness check: a message
can be confidently wrong.

The input is validated before the model loads: a missing `text` column, a blank
message or a duplicate id stops the run with exit status 2 and a message naming
the line. `examples/new_messages.csv` holds 18 messages written for this
project (none appears in Banking77). The first run embeds and caches the 9,993
Banking77 training messages (`results/cache/`); later runs reuse them.

## Usage

```python
from uneven_compression.ingestion import load_banking77, load_scifact
from uneven_compression.batching import make_batches

test = load_banking77("test")                 # 3,076 validated Requests
batches = make_batches(test, batch_size=32)   # 97 batches: 96 x 32, then 1 x 4

corpus, queries, qrels = load_scifact("test") # 5,183 docs, 300 judged queries
```

Any invalid record raises `ValidationError` and stops the load, so bad data
can never silently change the number of examples a run measures.

Banking77 is MTEB's current copy (`mteb/banking77`: 9,993 train / 3,076 test),
which differs from the original release by 14 rows. The published bge-small
Banking77 score used an older revision (`0fd18e25`, 10,003 / 3,080), so the
calibration step in `scripts/fp32_baseline.py` loads that revision separately.

## FP32 baseline

```bash
pip install -e ".[dev,model]"
python scripts/fp32_baseline.py     # writes results/fp32_baseline.json
```

Runs on CUDA, Apple MPS or CPU. Reports Banking77 accuracy, macro-F1 and
per-intent F1 (logistic regression on all training embeddings), a calibration
against the published score using MTEB's classification recipe, and SciFact
nDCG@10.

## Reproducing the results

INT8 and NF4 need bitsandbytes and a CUDA GPU, so the two GPU steps run on
Explorer's V100s; everything after them runs on any machine.

```bash
# on Explorer (GPU)
sbatch slurm/timing_v100.sbatch    # 16 settings -> results/timing/<job>/
sbatch slurm/embed_v100.sbatch     # vectors at 4 precisions -> results/embeddings/<job>/

# anywhere, after copying results/ back
pip install -e ".[dev,analysis]"
python scripts/score_quality.py results/embeddings/<job>     # -> results/quality/<job>.json
python scripts/analyze_quality.py <job>                      # -> results/analysis/<job>.json
python scripts/make_figures.py --timing <timing job> --quality <embed job>
```

The runs reported are timing job 12126225 and embedding job 12145703 (both
Tesla V100-SXM2-32GB, torch 2.5.1, transformers 4.49.0, same course container;
the timing run records bitsandbytes 0.50.2, the embedding run predates that field).
`results/` is not committed (large and regenerable); `run.json` in each run
folder records the node, GPU, library versions and arguments.
